# Deployment and Release

> **Current state.** These steps preserve the deployment and release
> instructions from the previous README. Items marked *unverified* have not
> been tested during this documentation pass.

## 1. Signaling server on Render

The phone camera needs a **secure context** (HTTPS) for `getUserMedia`, so
the server must be reachable over HTTPS. Render provides TLS termination.

1. Create a Render **Web Service** from this repository.
2. Build command: `npm install`
3. Start command: `npm run server` (runs `node server/server.js`)
4. Environment variables (see [CONFIGURATION.md](CONFIGURATION.md)):
   - `TRUST_PROXY=1`, so join rate limiting uses the real client IP from
     `X-Forwarded-For`.
   - `PUBLIC_ORIGIN` if the service is not
     `https://cam-share-app.onrender.com`.
   - Optionally `ICE_SERVERS` + `TURN_SECRET` for a TURN relay.
   - Optionally `MAX_CONNECTIONS`, `MAX_ROOMS`.
5. Render injects `PORT`; the server reads it.

Notes:
- The repository has no `render.yaml`; the service is configured in the
  Render dashboard. The live dashboard settings are **unverified** from the
  repo.
- `npm install` also installs the dev dependencies (`electron`,
  `electron-builder`) unless the platform omits them. The server only needs
  `ws`. Whether Render's build currently downloads the Electron binary is
  **unverified**.
- There is no dedicated health-check endpoint; `GET /` returns 200 with the
  landing page.
- All state (rooms, rate-limit counters) is in memory: restarts drop every
  pairing, and running more than one instance would split rooms across
  instances. Run a single instance.
- On Render's free tier the service sleeps when idle. The desktop app sends
  a wake-up `fetch` at startup and shows "Waking up cloud server (takes ~30s
  on cold start)…" if the socket has not opened after 4 s.

### Using a different domain

See [CONFIGURATION.md → Pointing the desktop app at a different server](CONFIGURATION.md#pointing-the-desktop-app-at-a-different-server).
The server, the desktop URL, and the desktop CSP all have to agree.

## 2. Running locally

```bash
npm install
npm run server          # http://localhost:8080
npm start               # Electron desktop app
```

By default the desktop app connects to the **production Render server**, not
to the local one. Running the local server in a way the desktop app and a
phone can use needs: `PUBLIC_ORIGIN` set to the local origin, `SERVER_URL`
for the desktop app, a CSP edit in `src/index.html`, and HTTPS reachable by
the phone (for example a tunnel). There is no ready-made local development
setup for this *(not tested)*.

## 3. Building the Windows installer

```bash
npm run dist
```

- Runs `electron-builder` using the `build` section of `package.json`.
- Output in `dist/`: `CamShare-Setup.exe` (NSIS, assisted installer with a
  choice of install directory), `CamShare-Setup.exe.blockmap`, `latest.yml`,
  and `win-unpacked/`.
- Last recorded build in `dist/`: version `0.1.0`, Electron `33.4.11`.
- Only Windows is configured. There is no `mac`/`dmg` target.
- No code signing is configured; Windows SmartScreen behaviour for the
  unsigned installer is **unverified**.
- `latest.yml`/blockmap are generated by electron-builder, but the app has no
  auto-updater (`electron-updater` is not a dependency).

## 4. Publishing the Windows download

The landing page's **Download for Windows** button links to:

```
https://github.com/mhmdbrkv/cam-share-app/releases/latest/download/CamShare-Setup.exe
```

1. Bump `version` in `package.json` if desired, then run `npm run dist`.
2. Create and publish a GitHub release in `mhmdbrkv/cam-share-app`.
3. Attach `dist/CamShare-Setup.exe` with **exactly that file name**. The
   link resolves to the latest *published* (non-draft, non-prerelease)
   release.

No release automation exists; this is a manual process.
